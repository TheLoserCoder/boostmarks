# Boostmarks project map

## Current state

The extension now has a working **bookmark projection**: the background service worker mirrors the native bookmark tree into IndexedDB (Dexie) and follows browser changes; the manager page renders that projection (cache-first) as an Explorer-style two-pane browser with quick links, breadcrumbs with an editable folder path, substring search and list/table/grid views. Bookmark moves are available via the context menu and pointer drag onto a folder in the current pane; capture, ranked/tag search and private folders are not built yet. `src/`, `web-ext/` and `webpack.config.js` are unported legacy code from `main`, kept for reference. Do not import legacy modules directly into new use cases. The other remote branch, `master`, contains an even older prototype. Do not delete either branch without explicit approval.

## Architecture and boundaries

- `app/features/bookmarks/` is the first capability module and the template for new ones: `domain/` (pure rules: tree flatten/assemble, event reconciliation, selection, folder-creation targets), `application/` (ports and the `bookmarkSync` use case), `adapters/` (Dexie store, `browser.bookmarks` source, page clients) and `ui/` (React components receiving a `ProjectionClient` prop). `app/features/i18n/` and `app/features/preferences/` follow the same split for the cross-cutting locale/theme concerns. Entrypoints are composition roots and own concrete wiring: manager, popup and options wrap their app in `AppRoot` and apply the stored theme before rendering. `app/ui/` is the shared design-system layer (tokens, Radix-based controls, menu/dialog/tooltip) used by manager, popup and options.
- WXT entrypoints live in `app/entrypoints/`: popup, manager, options and background. A content script will be added when opt-in capture is designed; do not request access to all URLs for an unused script.
- Manager UI: icon-first, Windows Explorer-inspired layout using one icon set (`lucide-react`). The manager frame starts with a real tab strip (currently one «Закладки» tab; no fake window controls), followed by full-width navigation (back/forward/up/refresh, breadcrumb/editable path field, search) and contextual command rows above the sidebar/content split. The manager **lands on Home**: `selectedId === null` renders `ui/HomeView.tsx` with cards for pinned entries and top-level folders (icon, name, honest caption — child count or URL host) plus an honest empty state; it shows no «Недавние» section because bookmark `dateAdded` is not a visit time. `null` is also a real entry in `domain/history.ts`, so «Назад» returns from the first folder to Home and Home is reachable from the sidebar's «Главная» entry; the «up» button stops at Home. Quick access = pinned ids persisted under `boostmarks:shortcuts:v1` plus top-level folders, resolved from the projection with missing targets dropped. The address field keeps clickable breadcrumbs inside an input-like Fluent surface and shows «Главная» when no folder is open; its chevron switches to direct text entry, Enter resolves paths by name (backslash separator), and duplicate names are reported as ambiguous, never guessed. Search is a plain substring filter over the projection until task 4 adds the worker and ranking. At ≤720 px the sidebar becomes a horizontal, internally scrolling strip and neither pane may exceed the window width.
- Row interaction follows Explorer conventions: single click selects, double click or Enter opens (folders navigate, bookmarks open in a new tab), ctrl/shift click and a marquee drag select multiple, arrows/Home/End move the roving focus, ctrl+A selects all and Escape clears. List and grid use listbox/option roles; the table uses grid/row/gridcell roles. Nested row controls stay out of the tab order, except the pin toggle.
- Native browser bookmarks are the source of truth for the ordinary tree. Dexie holds the projection and freshness metadata. Pages render the last saved projection before the background reconciles. `onRemoved` fires only for the removed folder, so descendants are pruned from the stored projection explicitly. A private tree must be encrypted and separate from native bookmarks.
- Mutations go through the `BookmarkCommands` port: pages send a typed message, the background adapter (`browserBookmarkCommands`) re-checks the parent and calls `browser.bookmarks.create`, and the projection follows through the ordinary `onCreated` event. Pages never write Dexie directly and never guess an id. Creating a folder offers `Новая папка` in the toolbar (when the open folder is writable) and in the content context menu, which resolves its target from the clicked row: a folder row targets that folder, a bookmark row its parent, the empty background the current folder. Names are trimmed and must not repeat an existing sibling folder name; the native root is not writable.
- Moving one bookmark or folder is also a typed `BookmarkCommands` request. The context-menu dialog accepts a full, unambiguous folder path; the UI rejects self/descendant and no-op moves, while the background re-reads native source and destination ancestry before `browser.bookmarks.move`. The shared `canDropOn` rule in `domain/dropTarget.ts` decides drop acceptance for the UI (including adjacent «before» no-ops), and the native command re-checks. Pointer drag uses dnd-kit with the whole row body as the drag surface (the grip stays as affordance only; the 8 px activation distance keeps click/selection intact): drop onto a folder name in the content pane or quick access sidebar to move into it, or onto a bookmark name to place immediately before it in the same folder. A `DragOverlay` ghost follows the pointer, targets show accent outlines and forbidden targets a dashed danger outline; `DropRulesContext` carries the rules so sidebar and rows share one visual language. The DnD context belongs to the explorer shell; the menu offers folder-path moves and a keyboard-accessible «В начало папки» action. Drag completion announces readable item/folder names rather than native IDs. Positional commands re-read native children before computing the final index. `onMoved` shifts and persists sibling indexes, not just the moved row; pages never write Dexie directly. Dragging a row that is part of a multi-selection moves the whole selection sequentially in visual order: the group rule `canDropManyOn` accepts positional groups only as one block (an all-no-op block is rejected), every item must validate before the gesture is accepted, `unchanged` results are counted apart from real failures, and partial native failures are reported with counts. Optimistic writes are deliberately absent: rows wait for the native confirmation and the following projection event, and the status bar or alert reports the outcome honestly.
- Locale and theme are real, persisted preferences. `app/features/i18n/` holds the Russian dictionary (key source of truth), a complete typed English dictionary and a small translator with `Intl.PluralRules` plural forms; `app/features/preferences/` owns the validated `boostmarks:preferences:v1` record, resolves `system` against the OS and writes the concrete theme to `<html data-theme>` so the light/dark token blocks stay single-source. `AppRoot` in `features/shell` is the shared composition root: it provides preferences and the translator, follows OS theme changes while `system` is selected and reloads preferences changed in another extension page through the window `storage` event; manager, popup and options entrypoints wrap their app in it and apply the stored theme synchronously before first paint. The options page exposes language and theme as real radio groups; popup and options reuse the same layer instead of duplicating strings. No hardcoded Russian strings remain in the explorer UI; tests keep asserting the Russian output through the default locale.
- Styling uses one shared kit: design tokens in `app/ui/tokens.css` (dark first, matching the Stitch Explorer reference layers: `#181818` chrome, `#191919` sidebar, `#1e1e1e` content shell, `#202020` surfaces and `#282828` fields; `[data-theme='light']` and `[data-theme='dark']` keep compatible light/dark variants, selected by the preference layer), controls in `app/ui/controls.css`, overlays in `app/ui/overlays.css`. The manager shell styles live in `features/shell/shell.css` and `features/bookmarks/ui/explorer.css` (tab strip, sidebar, toolbar, status bar) while row/table/grid/drag styles live in `features/bookmarks/ui/content.css`. Grid rows align to the start and never stretch to fill the pane. DnD uses a short transform/opacity lift and 180 ms drop animation, both disabled by the global reduced-motion rule. Radix Primitives provide behaviour and ARIA semantics under app-owned styled components, so no browser-default control appearance remains while real `button`/`input` semantics stay.
- External bookmark calls do not participate in Dexie transactions; events are serialized through a single queue in `bookmarkSync`, and import completion triggers a full resync. Events for unknown ids are ignored and healed by the next hydration. Full Google Drive synchronization of native bookmarks requires a separate conflict design.
- React performance: use `vercel-react-best-practices`; list, table and search-result rows are windowed above 50 items (`VIRTUALIZE_ABOVE`) with `aria-posinset`/`aria-setsize` and `aria-rowcount`/`aria-rowindex` preserving true positions; the table view uses ARIA table roles because absolutely positioned native rows break layout. Grid virtualization is subtask 3.9; the search worker remains future work. Respect reduced motion and accessibility. Follow `clean-architecture` and `clean-code`.
- Visual direction: aim for an intuitive, Windows Explorer-inspired interface with a strong emphasis on recognizable icons; pair icons with readable labels or accessible names rather than relying on icons alone.

## Checks and development

- Install: `npm ci`. Local scripts: `npm run lint` (ESLint plus a 500-line physical file limit), `npm run check` (lint, TS, tests, Chromium and Firefox MV3 builds), `npm run test:e2e` (installed Chromium extension with isolated profile; covers popup navigation plus create/rename/delete-and-reload projection flow), `npm run test:firefox:lint` (Firefox package validator). Download isolated browsers with `npx playwright install chromium firefox`.
- Keep authored code files under **500 physical lines**, preferably much shorter; split by responsibility before hitting the limit. `scripts/check-file-length.mjs` covers `app/`, `src/`, `tests/`, `scripts/` and root code/config; ESLint enforces the same ceiling for maintained JS/TS. Generated artifacts (`.output/`, `.wxt/`, `web-ext/`), copied external skills (`.agents/`), Task Master metadata and `package-lock.json` are exceptions because they are not authored application code. Legacy `src/` still has the line limit but is excluded from style rules until ported. If a genuinely indivisible authored file ever needs an exception, document its path and reason here and make the checker exception explicit, not a blanket directory exclusion.
- Firefox **runtime** E2E is still pending Task Master task 7: Playwright's Chromium extension loader does not load Firefox add-ons. Use `web-ext run --source-dir .output/firefox-mv3 --firefox <path-to-firefox> --no-reload` with a fresh profile for manual checks; add automated Firefox installation and behavior assertions separately. Firefox lint is not a runtime test.
- Do not call `chrome.runtime.reload()` on the unpacked review profile (`%LOCALAPPDATA%\Temp\opencode\boostmarks-review`): Chrome flags it `kDisableReload` (16777216) and disables the extension. To pick up a new build, close the window's Chrome processes (command line contains the profile path) and relaunch with `--load-extension`; the review profile already contains demo folders «Работа» and «Чтение» for manual drag checks.
- Use `test-driven-development` on every feature, bugfix, refactor and behavior change: write a failing behavior test, observe the expected failure, write minimal code, run the focused test and full suite, then refactor. Use real components and hand-checked expectations; mock only slow/external boundaries. New DB operations need fake-indexeddb integration tests and real-browser verification.
- For UI review, fetch the current `web-design-guidelines` and check focus, semantics, keyboard access and contrast. Use `analytics-strategy` for local statistics measurement design; do not add telemetry by default.
- Task Master state lives in `.taskmaster/`; consult/update existing tasks instead of duplicating them. Use CodeGraph for substantial cross-file work and dependency impact, but verify against source and tests. Document important architecture decisions in this **root AGENTS.md**, not README.md.

## Test scope

`tests/unit/` uses Vitest/Testing Library; `tests/unit/bookmarks/projection.perf.test.ts` measures scale (fixture: 50 folders × 1000 bookmarks). Baseline on this machine (2026-09-27, vitest, fake-indexeddb): flatten 50k nodes ≈ 10 ms, buildTree+topLevel ≈ 8 ms, folder-with-1000-children prune ≈ 5 ms, 20k-node IndexedDB write ≈ 600 ms / read ≈ 35 ms. `fake-indexeddb` timings are not real-browser numbers; real Chromium/Firefox UI timing and virtualization gates belong to tasks 3 and 7. `tests/unit/bookmarks/virtualization.test.tsx` stubs `ResizeObserver`, element offsets and `scrollTo` to exercise windowed list/table/search rendering plus keyboard walk inside the window; `tests/unit/bookmarks/selection.test.ts` covers the pure selection and marquee geometry rules; `tests/unit/ui/kit.test.tsx` covers the shared controls (labels, single tab stop, arrow selection, menu and dialog behaviour); `tests/unit/bookmarks/createFolder.test.ts` and `folderCommands.test.ts` cover target resolution, name validation and the native command adapters; `tests/e2e/large-folder.spec.ts` seeds a 150-bookmark folder in a real Chromium profile and asserts bounded DOM rows, keyboard focus movement and scrolling to the end; `tests/e2e/create-folder.spec.ts` creates folders through the context menu and toolbar and verifies the native tree; `tests/e2e/ui-kit.spec.ts` checks the segmented radio group in a real browser. `tests/e2e/` launches the real Chromium extension with a temporary profile; Firefox MV3 builds are validated by `web-ext lint` until runtime E2E is added. `playwright.config.ts` caps workers at 2 with a 10 s expect timeout because every test starts its own Chromium extension profile, and the projection needs a moment to hydrate before assertions.
`tests/unit/bookmarks/move.test.ts`, `moveCommands.test.ts` and `moveUi.test.tsx` cover move validation, the native/message boundary and the dialog. `tests/unit/bookmarks/moveBatch.test.ts` covers the sequential group move and Russian count forms; `dropTarget.test.ts` also covers the multi-selection rules. `tests/e2e/move.spec.ts` checks native moves and projection reconciliation in Chromium. The existing virtualization tests currently emit React `flushSync` warnings; they pass, but the warnings are not a clean run.
`tests/unit/bookmarks/reorderCommands.test.ts` covers native positional indexes and the typed message; `tests/unit/bookmarks/dropTarget.test.ts` covers the pure drop-acceptance rules; `tests/unit/bookmarks/history.test.ts` covers the navigation stack (including Home as an entry), `tests/unit/bookmarks/navigation.test.tsx` the toolbar, and `tests/unit/bookmarks/home.test.tsx` the landing view (cards, pinned section, empty state, Home fallback); `tests/e2e/drag-move.spec.ts` verifies drops onto a folder, before a bookmark in both directions, onto a pinned sidebar folder, dragging by the row name with the ghost overlay, multi-selection group moves with counts, forbidden group/self targets, and forbidden self-targets in Chromium; `tests/e2e/ui-kit.spec.ts` also checks the Home landing flow and that the narrow window's panes never exceed the viewport.
